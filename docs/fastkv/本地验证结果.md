# FastKV 本地验证结果（M1 Mac 9B）

> 依据 `远程部署与测试指引.md` 在**本地设备**（Apple Silicon M1 + Qwen3.5-9B-Q4_K_M）上可执行的实验实测记录。
> 与远程（RTX 5090 + Qwen3.6-35B）对比，突出**设备端 compact 优化**带来的改善。

---

## 测试环境（本地）

| 项目 | 说明 |
|------|------|
| 硬件 | Apple Silicon M1 Max |
| 模型 | `/Users/wh/Desktop/Qwen3.5-9B-Q4_K_M/Qwen3.5-9B-Q4_K_M.gguf`（Q4_K，~5.6 GB）|
| 数据 | `llama.cpp/wikitext-2-raw/wiki.test.raw`（标准 Wikitext-2）|
| 工具 | `llama.cpp/build/bin/llama-{cli,perplexity}`（fastkv 分支，HEAD `c3cbad31b`）|
| 后端 | Metal（默认全量下放）；含**设备端 compact**（`ggml_get_rows` gather）|

> 注：本地按用户约束**仅跑少量 chunks**（`--chunks 3`）验证，不做全量 72 chunk，因为 M1 上全量耗时过长且结论趋势已可比。

## 测试 A：功能验证（压缩是否生效）

**命令**：
```bash
./build/bin/llama-perplexity -m …/Qwen3.5-9B-Q4_K_M.gguf \
    -f …/wikitext-2-raw/wiki.test.raw -c 4096 --chunks 3 \
    --fastkv --fastkv-ratio 25 --verbose
```

**结果**（`-c 4096`，3 chunk）：
```
set_fastkv: FastKV enabled=1 retain_rate=0.25 window=8 kernel=7 pool=0
FastKV trigger: 7 次
fastkv_compact: compressed: 2048 -> 512 KV cells (saved 1536)
fastkv_compact: compressed: 2560 -> 1024 KV cells (saved 1536)   （与 2048->512 交替）
```

| 指标 | 本地实测 |
|------|---------|
| 压缩触发次数 | 7 次（3 chunk）|
| 压缩规律 | `2048 -> 512`（25%）与 `2560 -> 1024`（40% 累积）交替 |
| 保留率确认 | M/N = 512/2048 = **25%** ✓ |
| 崩溃 | 无 |

✅ **与文档预期完全一致**（触发、保留率、交替规律均相符）。

## 测试 B：困惑度质量（Wikitext-2 PPL）

**命令**（`-c 4096 --chunks 3 -s 7`，串行对比）：
```bash
# 基线
llama-perplexity -m …  -f …wiki.test.raw -c 4096 --chunks 3 -s 7
# FastKV 各比例
for r in 25 50 75; do llama-perplexity -m … -f …wiki.test.raw -c 4096 --chunks 3 -s 7 \
    --fastkv --fastkv-ratio $r; done
```

**结果（本地 9B）**：

| 配置 | PPL | ΔPPL vs 基线 | 远程 35B Δ |
|------|-----|-------------|-----------|
| 基线 | **6.4636** ±0.202 | — | — |
| ratio=25 | 6.7028 | +0.239 (**+3.7%**) | +3.9% |
| ratio=50 | 6.6208 | +0.157 (**+2.4%**) | +2.8% |
| ratio=75 | 6.5936 | +0.130 (**+2.0%**) | +1.7% |

✅ **单调且与远程一致**：保留越多，PPL 越接近基线；25% 损失最大（+3.7%）。本地 9B 与远程 35B 的 ΔPPL 趋势、量级高度吻合，证明 FastKV 压缩规律在模型规模间可复现。

## 测试 C：下游任务（HellaSwag/Winogrande）— 跳过的理由

文档已明确：HellaSwag/Winogrande 任务极短（几十 token），`-c 4096` 下 budget 远超单任务 prefill，**FastKV 从不触发压缩**，四组 acc 完全相同，**无开/关对比价值**。且需额外下载数据（本地网络对 HF/GitHub 间歇阻断）。故本地不做数据下载与重复测量，直接采纳文档结论。

## 测试 D：长上下文性能（llama-cli）

**样本**：`test_data/wk_sample_8k.txt`（wiki.test.raw 前 20000 字符 ≈ 3901 词 / ~4K token，8K 上下文）。

**命令**（`-c 8192 -n 32 -s 7`，开/关 FastKV 对比）：
```bash
llama-cli -m …  -f test_data/wk_sample_8k.txt -n 32 -st --no-display-prompt -c 8192 -s 7
llama-cli -m …  -f test_data/wk_sample_8k.txt -n 32 -st --no-display-prompt -c 8192 -s 7 \
    --fastkv --fastkv-ratio 25 --verbose
llama-cli -m …  -f test_data/wk_sample_8k.txt -n 32 -st --no-display-prompt -c 8192 -s 7 \
    --fastkv --fastkv-ratio 50 --verbose
```

**结果（本地 9B，8K ctx）**：

| 配置 | Prompt t/s | Generation t/s | KV 压缩 | 远程 35B Prompt 降幅 |
|------|-----------|---------------|---------|---------------------|
| 基线 | **319.8** | 24.8 | 无 | — |
| ratio=25 | 298.5 | **26.2** | 2048→512, 2512→1012 | −29% |
| ratio=50 | 289.3 | 23.5 | 2048→1024, 3024→2024 | −38% |

**解读（与远程对比的关键改善）**：
- **prefill 本地仅降 ~7% / ~9%**（319.8→298.5→289.3），**远小于远程 35B 的 −29% / −38%**。
  **直接原因：本地走设备端 compact（`ggml_get_rows` 设备端 gather），而无远程那版 host memcpy round-trip**。设备端优化把 FastKV 在文档里标记为"prefill 硬伤"的代价大幅压缩。
- **decode**：ratio=25 时 Generation 24.8→26.2（+5.6%），与远程 16K 的"decode 加速"方向一致（本地 8K 较短、`-n 32` 图短，幅度小且波动，参考性有限）。
- **压缩精确**：`2048→512`（25%）、`2048→1024`（50%）精确符合 ratio。

## 结论汇总（本地镜鉴）

| 文档结论项 | 本地验证状态 |
|-----------|------------|
| ✅ 功能触发 | **一致**：7 次 trigger，保留率精确 25%/50% |
| ✅ 质量保持（PPL）| **一致**：25%→+3.7%、50%→+2.4%、75%→+2.0%，单调、量级与远程相符 |
| ✅ 性能（prefill）| **显著改善**：本地仅降 7-9%（远程 29-56%），归功于设备端 compact |
| 下游任务 / 长文基准 | 未做（短任务不触发无对比价值 / 本地全量不可行），见测试 C/E 说明 |

## 设备端 compact 的本地意义
本地实测直接量化了 `c3cbad31b`（设备端 compact + 后端自适应）的价值：
- **prefill 从文档记录的"净亏损（−29% ~ −56%）"改善到本地仅 −7% ~ −9%**
- **同时 PPL 质量损失不变**（与远程一致），即**无损提速**
- 后端自适应（GPU 走设备端 gather、CPU 走 host）保证通用性
